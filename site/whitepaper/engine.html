Where it stands today

  • Pre-release. The packages are not on npm yet and the source repository is private while we finish the launch checklist.
  • Two machines, one browser. Every real-GPU result comes from Edge 155 on Windows 11: an Intel Arc 140V laptop and an NVIDIA RTX A6000 desktop. Firefox, Safari, macOS, Linux and Android are not verified. The demos were run by hand on an iPhone, with no scripted result.
  • WebGPU first. PBR, shadows, image-based lighting and most packages need WebGPU. An optional 2,711-byte package draws basic meshes on WebGL2.
  • No speed claim against three.js. We have a same-scene harness but no quiet-machine run committed yet. Section 5 explains what the early runs showed.

0Abstract

Margo Engine is a 3D engine for web applications written in TypeScript, with a Rust kernel compiled to WebAssembly and a WebGPU renderer. Core plus the high-level stage facade (createStage) measures 56,444 bytes minified and 22,253 bytes gzipped, and the build fails at 25,000. Everything else, from glTF PBR and shadows to post-processing, physics, CAD import and voxel worlds, lives in 81 optional, side-effect-free packages. A bundle contains only the packages it imports, and large runtimes such as OpenCascade or the Draco decoder are fetched only when a file needs them.

This paper covers the design, the size and performance we have measured, the tooling that keeps those measurements reproducible, and the limits we know about. Each figure names the result file it came from and the hardware it ran on. Where we have no committed measurement, we say so. A companion paper covers Margo Voxel, the voxel editor built on the engine.

import {createStage} from 'margoengine';
const app = await createStage('#scene');
const orb = app.sphere({color: '#84d6bd', roughness: 0.25});
app.onTick(delta => {orb.rotation.z += delta;});
window.addEventListener('pagehide', () => app.dispose(), {once: true});

1Design decisions

  1. A small core that stays frozen. Core and the stage are feature-frozen for 1.0. New capability goes into optional packages through the extension hooks in section 3. A feature that would need a new core API does not land, and CI rejects any pull request that pushes core + stage to 25,000 bytes gzip.
  2. Data-oriented transforms in Wasm. Positions, rotations, hierarchy, world matrices, bounds and culling live in flat typed arrays inside Wasm memory and are computed by one Rust function per frame.
  3. WebGPU first, guaranteed limits only. The device asks for no limit above WebGPU's guaranteed minimums. A scene that runs on the test laptop asks nothing of the GPU that a phone is allowed to refuse.
  4. Errors that name the fix. Packages throw a MargoError with a code, a TypeError or a RangeError, and the message says how to get past it: RangeError: Too many glTF nodes (100001 > 100000; raise the maxNodes option).
  5. No number without a source. Every published figure has a row in a claims inventory with its evidence and status (section 6).

2The kernel

packages/kernel/src/lib.rs is about 21 kB of no_std Rust compiled to Wasm. Each entity is a slot in a structure of arrays: position, rotation and scale, parent, local and world bounding spheres, world matrix, joint limits, a snapshot of last frame's inputs, and scratch space. That is 86 float32 columns and 7 flag bytes, or 351 bytes per slot. JavaScript writes transforms into views of that memory; nothing crosses the boundary per entity.

The tick follows three rules:

  • Recompute only what changed. An entity is recomputed when its transform, parent, bounds or hidden flag changed, along with its descendants. A static scene pays only for the input comparison, about 41 ns per entity on the test machine.
  • Publish nothing rather than something wrong. A bad quaternion, a zero scale, a non-finite parent or a hierarchy deeper than 64 yields no matrix. World matrices are written only after every node validates.
  • No allocation. The tick does not allocate. Growth happens outside it: the store starts at 1,024 slots and doubles on demand up to 223 (8,388,608) by creating a larger kernel at the same address and copying the columns back. A growth that cannot allocate throws and leaves the store as it was.

Two details reviewers usually ask about. Parent indexes are stored as float32, which is exact below 224, so the 223 cap keeps them exact. The world bounding sphere's radius is scaled by √(‖M‖1·‖M‖∞), an upper bound on the spectral norm of the transform, so culling never drops a visible object because of a skewed matrix.

The cost is linear. A test checks that dirty propagation produces the same world matrices and visibility, bit for bit, as a fresh full recompute, through growth from 1,024 to 1,048,576 slots, 63-deep chains, moves, removals and slot reuse.

3The renderer and its hooks

Core groups visible meshes by geometry and draws each group with one instanced draw call per pass, with per-instance material values. When the mesh set, materials, visibility and cull result are unchanged, it reuses last frame's instance lists and patches only the matrices that moved, and the renderer uploads only the changed range. The renderer uses reversed float depth, GPU picking with integer ids, and recovers from device loss; npm run visual:device-loss destroys the device mid-frame and checks that each of 24 demo views comes back.

A group whose instances are all single-sided and unmirrored draws through a second pipeline with hardware back-face culling and no discard in the shader. A discard anywhere in a fragment shader disables early depth testing, so removing it matters even for fragments that never take the branch. Frames are unchanged: 0 of 153,600 pixels differ across 13 test steps against the previous core.

Extension points

Passes
EnginePlugin frame-graph passes. Shadows, post effects, TAA and GPU culling attach with X.attach(engine, options).
Shader hooks
Packages patch core's WGSL at named points. Shader-contract tests fail when a patch no longer matches the text it expects.
Batch redirect
A pass sees the frame's batches in draw order and may set batch.redirect = {instances, args}; core then draws that batch from the package's records with drawIndexedIndirect. This hook cost 34 bytes gzip and lets GPU culling run on ordinary core meshes.
Raw state
Wasm memory and GPU objects are reachable only through the explicit @margoengine/core/extension entry, so the public API stays portable.

5Performance

Method

Headless Edge through Playwright, vsync and the frame-rate cap off (FPS is throughput, not a 60 Hz cap), cross-origin isolated for 5 µs timers, fixed canvas at DPR 1. GPU time comes from WebGPU timestamp queries injected into every pass. Each run records AC power at start and end and holds a GPU lock so only one GPU job runs at a time. A quiet gate waits until the CPU stays under 20% for 20 seconds. Before/after pairs alternate in rotating order within one session, because the same build varied by 10-40% between sessions. Runs on a mock GPU are labelled as CPU measurements and never reported as frame rates.

Five part shapes (a plate with eight holes, an L bracket, a bolt, a nut, a washer) instanced into 27-part modules under a five-level hierarchy, 936 distinct triangles, orbited by the camera. Large coordinates

Core stores positions in float32. With a 10 mm part 50 mm from the camera, core alone jitters 0.38 px at 1 km from the origin and 42 px at 100 km, and at 6,000 km the part is not drawn. FloatingOrigin (1,258 bytes gzip, no core change) holds jitter at 0.019 px at every distance up to 6,000 km, and picking still hits the part.

What we have not measured, and three.js

We do not claim Margo is faster than three.js. Our harness (examples/package-benchmarks/vs-threejs) pairs like with like: Margo core meshes against one three.js Mesh per object, and our instanced paths against InstancedMesh, with both engines timed by the same injected timestamp queries. The runs so far were diagnostics on a busy machine, so we do not quote their numbers. They pointed both ways. Core's automatic instancing used far less CPU than one Mesh per object, which is how most three.js code is written. On static instanced boxes, three.js's InstancedMesh beat our instanced paths in most cases. The same diagnostics found that our core never culled back faces in the pipeline, which led to the culled pipeline in section 3. A quiet-machine run of the full harness is the next measurement, and it will be committed with the places three.js wins.

Also not measured: discrete GPUs other than the RTX A6000, Apple GPUs, Android GPUs, Firefox and Safari.

6Keeping the numbers honest

A claims inventory

docs/whitepaper/claims.md lists every claim the public docs make or imply, 268 rows at the last recount, each with its evidence and a status. A claim is PROVEN only when a committed script and a committed result support its exact wording and no later code change invalidates it. The audit that built it found 23 claims that overstated their evidence and 58 with no committed evidence; all 23 were corrected or removed. Today the inventory reads 213 proven, 6 stale, 16 unproven (mostly internal notes), 0 overclaims, 18 removed and 15 kept only as dated history. Every row of the design-envelope page (section 8) is proven.

Proofs that a feature costs nothing when it is off

A recording GPU stands in for the WebGPU device and logs every call, descriptor, shader text and buffer write. A proof builds a baseline commit and a candidate and compares the two recordings exactly, with no tolerance. That is how we check claims such as "attaching nothing from this package leaves core's GPU work unchanged" or "this optimization issues the same calls in a different order". There are 51 proofs, each pinned to the commit that made its claim so later code cannot quietly break it. Twenty are ongoing guarantees that also run against the working tree in every npm run verify.

A deliberate change to a feature-off path advances that proof's reference, and the reason goes into the inventory. For example, when TAA's errors were converted to MargoError, exactly three of the 7,900 recorded entries changed (the error class and its text) and every GPU call, descriptor and buffer write stayed identical.

Pixels on real GPUs

The visual suite renders 55 views (32 Khronos sample models and 23 views of eight demos at different quality tiers) and compares them against references recorded per GPU and browser. The NVIDIA profile was captured four times from committed sources: 220 captures on AC power, 47 views byte-identical across all four runs. The tolerance per view is three times its measured run-to-run noise plus fixed allowances. A view captured on one GPU is never compared with references from another.

Hostile files

Every parser of untrusted input has a seeded, deterministic fuzzer (npm run fuzz): glTF and GLB, gltf-pro's worker and progressive stream, Draco, KTX2, meshopt, HDR, EXR, UltraHDR, FBX, OBJ, STL, PLY, 3MF, PCD, OFF, XYZ, VTK, USDA, USDC, USDZ, STEP, IGES, IFC, our own .margo format and network snapshots. An input passes if it returns or throws the package's own named error within its time budget, without growing memory by more than 64 MiB plus 64 times its size. Some of what it found, all fixed with regression tests:

  • A 314-byte PLY that declared millions of elements and allocated 336 MiB. Parsers now check that the body can hold the declared counts before allocating.
  • A 65 KB zip entry inside a 3MF that inflated to 64 MiB. Entries over 1 MiB may now expand at most 200x (real 3MF files measured at 9x).
  • 27-byte meshopt inputs that asked for 1-2 GiB of output.
  • IFC files that send web-ifc's Wasm into an endless loop. Syntax is now checked first, and untrusted IFC can run in a worker that is killed at a deadline.
  • A glTF primitive without normals whose coordinates passed 1019, which overflowed the summed face normals to Infinity and left NaN in the vertex data.

Security review

A review of the attack surface found and fixed, each with a regression test: model files whose buffer and image URIs escaped their directory (a model could make the viewer request intranet or same-origin endpoints with cookies; URIs are now confined to the model's directory unless the app allows more); a regular expression in the STL reader that rescanned to the end of the file for every unterminated facet (0.84 s for a 380 KB file, quadratic beyond that); and a glTF accessor of "type": "constructor" that resolved through the object prototype, made sizes NaN and silently switched off the decoded-memory budget. Keys named __proto__, constructor and prototype are dropped from glTF and .margo JSON at every depth. Nothing in the engine needs 'unsafe-eval'; the Wasm kernel needs 'wasm-unsafe-eval', and a strict policy on the page and every worker ran with zero violations in Edge.

7CAD and engineering

CAD viewing is the use the engine was tuned for. @margoengine/machinery provides section planes with capped solids, feature edges, exploded views, measurement and dimensions, kinematic joints and conveyor simulation. Around it: an assembly BVH for fast picking, a view cube, orthographic and exactly top-down cameras, and the GPU culling described above.

STEP today, through OpenCascade

STEP and IGES currently load through OpenCascade (occt-import-js 0.0.23, LGPL-2.1) in a worker that starts only when such a file arrives. The cost is real: a 7,604,031-byte Wasm (3,114,121 gzip), and 1.4-1.7 seconds from request to model for a 442 kB STEP file. The lighter path converts at build time: margo-convert turns that file into a 68,352-byte GLB that loads without OpenCascade.

examples/package-benchmarks/cad/results-step.json · margo-convert-diagnostic.json

Our own kernel

@margoengine/brep is a B-rep kernel written from the published standards (ISO 10303-21 for the file format, ISO 10303-42 for geometry and topology, the AP203, AP214 and AP242 schemas) and textbook geometry, without reading OpenCascade's source. It reads STEP, ACIS SAT, Parasolid XT and JT 9.5+, evaluates analytic and NURBS curves and surfaces exactly, and meshes each body without cracks: every edge is discretized once and shared by both faces, and each face's domain gets a constrained Delaunay triangulation with Shewchuk's robust predicates. It checks its meshes against the volume, area and centroid many STEP files state about themselves. A first cut of modeling (Booleans, fillets and chamfers, exact mass properties) is in the package too.

@margoengine/brep is available under a dual AGPLv3 / Commercial proprietary license for enterprise integrations. We compare it with OpenCascade file by file and operation by operation in our own harness, but those runs are not committed yet, so this paper makes no speed or completeness claim for it. OpenCascade still leads on freeform NURBS-to-NURBS intersection, advanced blends and healing broken files.

9What is not done

  • Publishing. The packages, the npm create margo starter and the public repository are waiting on the launch checklist.
  • A fair speed comparison. The quiet-machine run of the three.js harness, on more than one GPU.
  • Code hygiene. Our own scorer (no any in public APIs, TSDoc on every export, the error conventions) rates the codebase 6.8 out of 10 against a launch gate of 9. Some packages score 10; others do not yet.
  • Coverage. Firefox, Safari, macOS, Linux, Android, and discrete GPUs beyond one RTX A6000.
  • WebGL2. A full WebGL2 fallback for the optional packages is planned for the next version, at zero core bytes. Today it draws core meshes only, flat-shaded with one light.
  • Multiple views and scenes on one engine is the next feature after the current visual-parity work.
  • Replacing OpenCascade with @margoengine/brep once it matches on our STEP corpus.

10Reproduce
