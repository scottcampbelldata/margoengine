Where it stands today

  • Coming soon. The packages are not on npm yet, and the source repository stays private while we finish the launch checklist.
  • WebGPU only, for now. About 88% of browsers in use support WebGPU: 85.8% fully and 2.02% partly (caniuse.com/webgpu, StatCounter data for September 2026). A WebGL2 fallback for the optional packages is planned. Today an optional package draws basic meshes on WebGL2.
  • One browser verified. Every real-GPU result comes from Edge on Windows 11. Firefox, Safari, macOS, Linux and phones are not verified yet.
  • No speed claims against other engines. The same-scene comparison tool exists, but no quiet-machine run has been made. The numbers on this page are our own internal measurements, and each names its hardware.

0Abstract

Margo Engine is a 3D engine for web applications, written in TypeScript. It has a Rust kernel compiled to WebAssembly and a WebGPU renderer. Core plus the high-level stage (createStage) measures 57,590 bytes minified and 22,737 bytes gzipped. The build fails at 25,000.

Everything else lives in 78 optional, side-effect-free packages: glTF PBR, shadows, post-processing, physics, CAD, voxel worlds with multiplayer, a path tracer, exporters and React. A bundle contains only the packages it imports, and large runtimes load only when a file needs them.

This paper covers the design, what we have measured, how the engine was built, and the limits we know about. Each figure names the file it came from. Where we have no committed measurement, we say so. A companion paper covers Margo Voxel.

import {createStage} from 'margoengine';
const app = await createStage('#scene');
const orb = app.sphere({color: '#84d6bd', roughness: 0.25});
app.onTick(delta => {orb.rotation.z += delta;});
window.addEventListener('pagehide', () => app.dispose(), {once: true});

1One install, kits and starters

npm i margoengine installs the whole engine. Its root is the stage, and every entry of every package is margoengine/<package>, one export * line each, so an app still bundles only what it imports. A test checks that the alias and the package bundle to the same bytes.

2Design decisions

  1. A small core that stays small. New capability goes into optional packages through the extension hooks in section 4. CI rejects any change that pushes core + stage to 25,000 bytes gzip. Multiple views and scenes were the one approved exception: 867 bytes gzip with the kernel changes that came with them (section 4).
  2. Data-oriented transforms in Wasm. Positions, rotations, hierarchy, world matrices, bounds and culling live in flat typed arrays in Wasm memory, computed by one Rust function per frame.
  3. WebGPU first, guaranteed limits only. The device asks for no limit above WebGPU's guaranteed minimums, so a scene asks nothing of the GPU that a phone is allowed to refuse.
  4. Errors that name the fix. Packages throw a MargoError with a code, a TypeError or a RangeError, and the message says how to get past it: RangeError: Too many glTF nodes (100001 > 100000; raise the maxNodes option).
  5. No number without a source. Every published figure has a row in a claims inventory with its evidence and status (section 9).

3The kernel

packages/kernel/src/lib.rs is no_std Rust compiled to Wasm. Each entity is a slot in a structure of arrays: position, rotation and scale, parent, local and world bounding spheres, world matrix, joint limits, last frame's inputs and scratch space. JavaScript writes transforms into views of that memory; nothing crosses the boundary per entity.

The tick follows three rules:

  • Recompute only what changed. An entity is recomputed when its transform, parent, bounds or hidden flag changed, along with its descendants. A static scene pays only for the input comparison, about 41 ns per entity on the test machine.
  • Publish nothing rather than something wrong. A bad quaternion, a zero scale, a non-finite parent or a hierarchy deeper than 64 yields no matrix. World matrices are written only after every node validates.
  • No allocation. The store starts at 1,024 slots and doubles on demand up to 223 (8,388,608) outside the tick. A growth that cannot allocate throws and leaves the store as it was.

The cost is linear. A test checks that dirty propagation produces the same world matrices and visibility, bit for bit, as a fresh full recompute, through growth to 1,048,576 slots, 63-deep chains, moves, removals and slot reuse.

4The renderer, views and hooks

Core groups visible meshes by geometry and draws each group with one instanced call, with per-instance material values. When nothing changed, it reuses last frame's instance lists and uploads only the matrices that moved. A group of single-sided, unmirrored instances draws with hardware back-face culling and no discard, which keeps early depth testing on. The renderer uses reversed float depth and GPU picking with integer ids, and it recovers from device loss.

Multiple views and scenes

One engine draws several views of one scene in a frame: split screen, the four-view CAD layout, picture-in-picture, a minimap. It also draws separate scenes: a HUD with its own objects and lighting, an item preview in a menu, a portal rendered to a texture. Effects with history keep it per view, and every package is view-aware. This is in core, as an approved exception to the size freeze. It added 867 bytes gzip to core + stage, because a smaller kernel paid for most of the 2.7 KB of new code. Core + stage is now 22,737 bytes, 2,263 under the gate. npm run check:views draws views on a real GPU and checks pixels, picks and validation errors in every merge.

Extension points

Passes
EnginePlugin frame-graph passes. Shadows, post effects, TAA and GPU culling attach with X.attach(engine, options).
Shader hooks
Packages patch core's WGSL at named points; shader-contract tests fail when a patch no longer matches the text it expects.
Batch redirect
A pass may set batch.redirect = {instances, args}; core then draws that batch from the package's records with drawIndexedIndirect. This lets GPU culling run on ordinary core meshes.
Raw state
Wasm memory and GPU objects are reachable only through @margoengine/core/extension, so the public API stays portable.

Every other entry and worker, and every lazily loaded file, is in the same record and on margoengine.com/sizes. We do not call Margo the smallest engine. We publish our method and our numbers. A size comparison with other engines will be run with the same build settings from the folder where those engines live (npm run bench -- size --engines=all), and published with its method when it has been run.

CAD import

STEP and IGES load through OpenCascade, compiled to WebAssembly by occt-import-js. The importer runs in a worker and is fetched only when a STEP or IGES file is, so it adds nothing to the core size; the OpenCascade .wasm is 7,604,031 bytes (3,110,912 gzip). Its triangles become core meshes in meters, with OpenCascade's surface normals. OpenCascade is LGPL-2.1 with the Open CASCADE exception; its two files ship unmodified apart from a CSP-safe change to the JavaScript glue, separate from Margo's code, so an application can serve its own build instead. margo-convert turns STEP into a GLB at build time for pages that should not load OpenCascade at all.

7Internal measurements

These are measurements of Margo against earlier Margo, on named hardware. They are not comparisons with other engines. The method: headless Edge with vsync and the frame cap off, WebGPU timestamp queries on every pass, a GPU lock so only one GPU job runs at a time, and a quiet-machine gate. Our benchmark tool, npm run bench, now runs every such measurement this way.

8How it was built

Margo is built by one person directing AI. Scott Campbell sets the goals, the rules and the gates; Claude, Anthropic's model, writes the code, the tests and the measurements in many parallel sessions. That only works if the process makes mistakes visible. These are the rules and the evidence that they hold.

  • Written rules every session reads. AGENTS.md is binding on every session. It sets the core size gate, the clean-room rule, one branch (main), and the checks every change must pass before it lands.
  • Clean room. No files from other repositories, under any licence. Code is written from public specifications, papers and descriptions. When a 2026-10-21 audit found areas close to other engines' or libraries' code, each was rewritten from a words-only spec by sessions that never saw the old code. That covered geometry, controls, text, shading terms, decoders, path finding and more (docs/HANDOFF.md, landed 2026-10-24). Other engines are run only from their own folder for benchmarks, never copied in. The few standard files every engine uses, such as sample models and prebuilt decoders, are listed with source and licence in THIRD-PARTY-NOTICES.md.
  • Gates that only ratchet. npm run quality runs in every verify and in CI. It holds five ratchets: entry sizes and heavy static imports, duplicated code between packages, packages and entries with no test, TSDoc and error conventions, and the clean-room checks. Each can only shrink unless a change records its reason. npm run hygiene scores eight more code gates per package.
  • Every bug fixed with a test. A fix lands with a regression test that fails without it. The fuzzers, the security review and the GPU checks in section 9 each produced fixes that way. The benchmark tool found one this week: shadow casters were drawn one by one, and the fix shipped with a test pinning the batched draws.
  • Honest reporting. Sessions report measured numbers only, label anything measured on a busy machine as such, and say when a check could not run.

We tell this because it is how the engine was made, not because AI makes the engine better. The evidence for the engine is the same as for any engine: the tests, the measurements and the code.

9Keeping the numbers honest

Tests and checks

  • 5,059 Node tests in every npm run verify, all passing at 8cc9e939 (results/test-count.json).
  • 51 GPU-call proofs. A recording GPU logs every call, descriptor, shader and buffer write, and a proof compares a baseline commit with a candidate exactly. That checks claims such as "attaching nothing from this package leaves core's GPU work unchanged". Each proof is pinned to the commit that made its claim, and 20 run against the working tree in every merge.
  • Pixels on a real GPU. The visual check renders 62 views of sample models and demos and compares them with references captured four times per GPU and browser. A view is never compared with references from another GPU (tests/visual/profiles/).
  • Every shader compiled. npm run check:wgsl compiles every WGSL source the packages hold on the browser's WebGPU, with feature flags both on and off, including shaders no view draws.
  • Hostile files. Every parser of untrusted input has a seeded fuzzer: glTF, Draco, KTX2, meshopt, HDR, EXR, FBX, OBJ, STL, PLY, 3MF, USD, STEP, IGES, IFC and network snapshots. Its findings were fixed with regression tests. Examples: a 314-byte PLY that allocated 336 MiB, a 3MF zip entry that inflated 1,000-fold, and IFC files that looped forever.
  • Security. A review fixed model files whose URIs escaped their directory, a quadratic regular expression in the STL reader, and glTF keys that reached the object prototype. Nothing in the engine needs 'unsafe-eval'; the Wasm kernel needs 'wasm-unsafe-eval', and a strict policy on the page and every worker ran with zero violations in Edge (docs/security.md, results/csp-check.json).

A claims inventory

docs/whitepaper/claims.md lists every claim the public docs make or imply, with its evidence and a status. A claim is PROVEN only when a committed script and a committed result support its exact wording. The audit that built it corrected or removed every claim that overstated its evidence.

The words we do not use, and why:

  • "first" or "only": we have not surveyed every engine;
  • "smallest": not without a published method and measurement;
  • "drop-in replacement": the API is our own;
  • "production-ready" or "runs everywhere": section 10 says why not yet;
  • faster than any other engine: no quiet-machine comparison has been run.

10Honest limits

  • WebGPU only today. PBR, shadows, image-based lighting and most packages need WebGPU, which about 88% of browsers in use support (caniuse.com/webgpu, September 2026). A WebGL2 fallback for the optional packages is planned; today WebGL2 draws basic meshes only.
  • Not yet verified on Firefox, Safari, macOS, Linux, Android or iPhone. Real-GPU results come from Edge on Windows 11, on an Intel Arc 140V laptop and an NVIDIA RTX A6000 desktop.
  • CAD import is tessellation only. STEP and IGES become triangle meshes through OpenCascade; the exact geometry is not kept, and the 3.1 MB (gzip) OpenCascade download comes with the first CAD file.
  • No editor yet. Scenes are built in code or imported from files.
  • No comparison with other engines yet. The tool runs the same scenes in other engines, interleaved on one machine, but the quiet-machine runs have not been made. Until they are, we make no speed claim against any other engine.
  • Next.js production builds need Rapier installed today, because the React package's root reaches it. The React package is being split so they do not.
  • Design envelope. 8,388,608 entities; 100,000 nodes per file by default; 16 textures per shader stage; float32 coordinates without FloatingOrigin. Every limit, with the error it raises and the package that takes you past it, is in docs/limits.md.

12Reproduce

From a checkout (Node 22.12+ or 24+). Each command writes or prints the figure it backs; GPU commands take the shared GPU lock.

npm ci
npm run build:packages
npm run measure:size          # core + stage gzip, fails at 25,000
npm run verify                # the 5,059 tests, quality gates, API reports, current proofs
npm run bench                 # every benchmark suite (docs/benchmarking.md)
npm run proofs                # all 51 pinned GPU-call proofs
npm run fuzz -- --short       # every parser fuzzer, 4 s each
npm run check:merge           # verify + site, visual, views, WGSL and packed-package checks (GPU)

Per-claim commands are in docs/whitepaper/reproduce.md.
