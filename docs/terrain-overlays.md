# Ground-clamped vector overlays

`@margoengine/terrain/overlays` exports `TerrainOverlays`, its metre-based position/style types, and GeoJSON import options. Attach the collection to a live `TerrainVirtualTexture` on the same engine. `addPolyline`, `addPolygon` and `addGeoJSON` return stable overlay IDs. `setPolyline`, `setPolygon`, `setGeoJSON` and `setStyle` update them without changing paint order. `move` changes bottom-to-top order; `remove` restores the underlying ground. Inputs are copied and validation is atomic. `order` and `length` describe user overlays; one GeoJSON collection can contain many GPU primitives.

Strokes use a width in world XZ metres with round joins and caps. A one-position direct stroke draws a round point. Polygons support concavity and holes with an even-odd fill independent of winding direction. Direct polygon rings close automatically; GeoJSON rings must already be closed as RFC 7946 requires. Altitude is ignored by the drape. Geometry follows the actual terrain through its shading texture, without elevated line meshes, height resampling, tessellation seams or depth-offset fighting. Widths are horizontal world-map metres, rather than pixels or distance measured along a steep terrain face.

GeoJSON accepts Point, MultiPoint, LineString, MultiLineString, Polygon, MultiPolygon, GeometryCollection, Feature and FeatureCollection, including null feature geometries and empty collections. A required `project` callback maps longitude/latitude degrees into the consuming terrain's local XZ metres. This keeps the terrain package independent of a particular local CRS or world origin. Features can share a style or use a property-based style callback. Positions must contain finite longitude/latitude in their standard ranges, with optional altitude. Antimeridian-cut geometry and projection choice remain the caller's responsibility, as specified by RFC 7946. Inputs are objects; fetching and JSON decoding belong to the application.

The RVT now accepts ordered surface providers through `addSurface` and exposes `refreshSurfaces` for providers whose shader declarations or binding sets change. The bake's group 2 and the reader's group 1 describe the same resources. Providers wrap `terrainSurfaceColor` before the surface function returns; they share position and footprint arguments. TerrainOverlays hides this protocol behind its typed API. The same coverage function also runs in the uncached reader fallback, so vectors remain visible past the cache and on steep faces. Other materials reading the RVT see the painted ground too. Decals retain their existing position above the surface-provider stack.

To put imagery under vectors in this cache, attach `TerrainImagery` with its new `virtualTexture` option before attaching overlays. Layer-set changes refresh the RVT shader/layout; style changes and decoded tiles invalidate the cache. Image factories and the RVT are borrowed. Collection disposal unregisters its provider, frees its GPU storage and removes its own scene registration; it leaves the borrowed terrain/RVT attached. Device restoration reuploads the retained vector data without duplicating registration.

Defaults: 4,096 independent primitives, 65,536 segments, half a cache texel of edge filtering, storage binding 120, linear RGBA [1,0.25,0,1] and width 2 m. Limits: 1..65,536 primitives, 1..1,048,576 segments, filter half-width 0..2 texels and binding 0..999, further bounded by device storage limits. A second collection needs a distinct binding. Storage holds one header, three vec4 records per primitive, and one vec4 per segment, so it uses `16 * (1 + 3 * primitives + segments)` bytes. Bounds reject unrelated primitives before segment tests. No claim of a spatial acceleration hierarchy, geodesic globe strokes, dash patterns or selectable miter joins is made.

Edits invalidate old and new footprints, including stroke half-width and the coarsest level's antialias margin. The next frame uploads metadata and bakes those regions; an unchanged frame bakes nothing. Tests count work, without wall-clock budgets: the native fixture paints 20,852 texels after its initial vector edits and 16,548 after a width change, compared with 262,144 for its four whole cache levels. These are fixture work counts, not speed results.

Evidence is `packages/terrain/test/overlays.test.js` and `overlays.browser.mjs`, plus the complete terrain CPU and GPU suites. CPU tests cover every GeoJSON family, projection, style, holes, input ownership, limits, restore, provider ordering and malformed live updates. Native WebGPU and WebGL2 compatibility tests render both cached and forced-fallback terrain, probe metre widths and polygon holes, compare imported GeoJSON with direct vectors, and require removal and empty updates to restore imagery exactly. A later imagery layer set is added and removed after the first frame to prove layout refresh. Actual terrain pixels use rendered red/green references through the engine's PBR Neutral display transform. Real scene data is the existing CC0 Poly Haven Aerial Rocks 02 photograph and Mapzen/USGS public-domain Rainier elevation, with their existing third-party notices. Analytic vectors supply independent coverage fixtures; no rival code or assets are used.
