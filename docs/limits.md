# Design envelope

Margo is a small WebGPU engine: core plus the stage facade is 22,781 B gzip (`npm run measure:size` prints the exact figure; the build fails at 25,000 bytes), and every
other capability is an optional package. That size is a decision, and so are the boundaries below. Each one exists
for one of two reasons: it keeps core small and frozen, or it follows the limits WebGPU guarantees on every adapter
(Margo's device requests none above them, so an app that runs on a laptop also runs on a phone). This page lists every
hard limit, where it starts, what you see when you reach it, and the package or tool that takes you past it.

How to read "Starts at":

- **Enforced**: an exact constant in the source (linked), usually with the test that asserts it.
- **Measured**: a committed result file (linked). Unless a row says otherwise: ASUS Zenbook S 14, Intel Core Ultra 7
  258V with an Intel Arc 140V integrated GPU, Windows 11, Edge 155, AC power, GPU lock held.
- **Not measured**: the boundary exists, but nobody has run the case. No number is given.

Every number here has a row in [whitepaper/claims.md](whitepaper/claims.md) (LIM-001 to LIM-030). Past losses and their
fixes are in [whitepaper/perf-history.md](whitepaper/perf-history.md).

## Scale

| Limit | Starts at | Why | What you see | Escape hatch |
| --- | --- | --- | --- | --- |
| Entities (core meshes, assembly nodes included) | Enforced: 8,388,608 slots (2^23; [kernel.ts](../packages/core/src/kernel.ts), [core-dirty-transforms.test.js](../tests/core-dirty-transforms.test.js)). The store starts at `capacity` (default 1,024) and doubles on demand. Measured ([results-scale-node.json](../examples/package-benchmarks/cad/results-scale-node.json), Node 24, quiet-gated): 352.1 B of kernel memory per slot at 1,048,576 slots (351 B by layout); a static kernel tick costs 3.3 ms at 100,006 entities, 20.2 ms at 499,992 and 41.5 ms at 1,000,012. Above 1,048,576 slots: not measured. | One float32 structure-of-arrays Wasm kernel computes every transform, bound and visibility. It is the reason core is small and fast, and its per-entity cost is linear: about 41 ns per entity per frame even when nothing moves. | Growth is automatic. Past the cap `createMesh` throws `RangeError: Capacity`; `Engine.create` with a larger `capacity` throws `RangeError: Capacity: 1..8388608`. A growth that cannot allocate throws and leaves the store as it was. Before the cap, frame time grows with entity count. | `@margoengine/culling`. `CulledInstances` keeps parts out of the entity store entirely: 0.41-0.55 ms CPU per frame at 89,883 parts, flat in part count ([results-culling.json](../examples/package-benchmarks/cad/results-culling.json)); parts lose picking, hierarchy and section caps. `CulledMeshes` GPU-culls parts that must stay core meshes ([cad-performance.md](cad-performance.md#gpu-culling-of-core-meshes-culledmeshes)); it removes GPU work, not the kernel tick: with `minRadius: 1.5` a 100,008-part orbit draws 11 % of the parts at 138 FPS (core: 29) ([results-5l-after-culled1.5.json](../examples/package-benchmarks/cad/results-5l-after-culled1.5.json)). |
| Nodes and parts per file in packages | Enforced, default 100,000 ([limits.js](../packages/shared/limits.js), [count-limits.test.js](../tests/count-limits.test.js)): glTF nodes ([gltf](../packages/gltf/src/index.ts), [gltf-pro asset.ts](../packages/gltf-pro/src/asset.ts)), `.margo` nodes ([blender](../packages/blender/src/index.ts)), OBJ parts and STEP/IGES meshes ([machinery cad-parser.ts](../packages/machinery/src/cad-parser.ts), [cad-worker.ts](../packages/machinery/src/workers/cad-worker.ts)), `SurfacePhysics` parts and carriers ([machinery surface.ts](../packages/machinery/src/surface.ts)). | Input validation that bounds memory for untrusted files: every node or part becomes a core mesh. | `RangeError: Too many glTF nodes (100001 > 100000; raise the maxNodes option)`; likewise `Too many .margo nodes` (`maxNodes`), `OBJ part limit` and `Too many CAD parts` (`maxParts`), `Too many surface parts` and `Too many surface carriers` (`maxParts`). | The option the error names, up to core's 8,388,608 entities: `maxNodes` on the glTF, gltf-pro and `.margo` loaders, `maxParts` on `loadCAD`/`parseCAD` and `SurfacePhysics.create`; a value outside 1 to 8,388,608 throws `maxNodes must be an integer from 1 to 8388608`. Load time and memory past 100,000: not measured. |
| Buffers per geometry | Enforced: a geometry's vertex, index and instance buffers (96 B per instance) must each fit the device's `maxBufferSize`; core requests the WebGPU default ([renderer.ts](../packages/core/src/renderer.ts)). Not measured. | WebGPU's guaranteed limits, so the same scene runs on every adapter. | `RangeError: GPU buffer limit` when the geometry is first drawn. | Split the geometry, or draw the copies with `CulledInstances`. |
| Shader variants per engine | Enforced: 64 cached pipeline variants ([renderer.ts](../packages/core/src/renderer.ts)). How close real scenes come: not measured. | Bounds pipeline compilation and memory. Variants come from MSAA, target format and shader text; each pick shader text (`engine.pick` with the scene's pass hooks) is one more. | `RangeError: Shader limit: 64`. | Not needed so far; fewer distinct shader patches per engine. |
| Voxel worlds and render distance | Measured ([voxel-sandbox-bench.json](../examples/package-benchmarks/results/voxel-sandbox-bench.json), RTX A6000 desktop, Edge 155, 1920 × 1080, 4x MSAA, quiet-gated, `examples/voxel-sandbox` seed 1): render distance 8 (1,379 chunks loaded, 602 with quads, 1.18 M quads, 14.5 MB of quads on the GPU, 15.9 MB of chunk data, 322 draws) fills in 1.06-1.22 s with frame CPU 0.7 ms median, 1.1 ms p95; render distance 16 (5,579 loaded, 2,435 with quads, 4.84 M quads, 59.5 MB, 64.1 MB, 1,170 draws) fills in 3.59-3.67 s (8.8-9.2 s before 2026-10-20) with 1.7 ms median, 2.2 ms p95 right after the third fill (1.3 ms median once settled, about 4 s later). While the world fills (the sandbox joins 2 ms of chunks a frame then) frame CPU is 4.2 ms median, 8.8 ms p95 at render distance 8 and 6.6 / 11.1 ms at 16, worst 15.8 ms. Flying at 11 blocks/s while chunks stream in: frame CPU p95 3.7 ms (render distance 8) and 5.0 ms (16), worst frames 6.8 and 10.2 ms; back to back with the code before 2026-10-20 at 16: 4.2 / 8.1 ms before, 3.9 / 7.4 ms after. Voxel GPU time from timestamps between passes is rough: 0.39-2.56 ms median at render distance 8 and 0.72-1.51 ms at 16 over three runs. Laptops and phones: not measured. | Each loaded chunk keeps its block palette and light on the CPU; each chunk with faces keeps 12-byte quads in one GPU pool (`maxQuadBytes`, default 96 MiB); generation and meshing run in workers, joining and light on the main thread spread over frames (`chunksPerFrame`, `frameBudget`); chunks above a column's ceiling, when the generator gives one, load as air without a job. | Filling the range takes time in proportion to the chunks in it, about 1,550 chunks a second here with a 2 ms join budget (about 680 with the default 0.5 ms, which keeps frames light during play). A full quad pool leaves far chunks unmeshed until near ones free pages. Worlds wider than float32 precision (about 100 km) jitter: voxels have no floating origin in v1 (packages/voxel/DESIGN.md, decision 4). | A smaller `distance` on `VoxelStreamer`; a larger `frameBudget` and `chunksPerFrame` while a loading screen shows; a larger `maxQuadBytes` (up to the device's storage binding limit); more `workers` for the mesher and streamer. |
| Voxel slabs and stairs | Measured (Node on the RTX A6000 desktop, `npm run bench -- voxel`): meshing the 128-chunk bench terrain takes 85.5-86.1 ms with slabs and stairs on two thirds of its surface (`mesh-128-shaped-chunks`; 78.2-79.2 ms before waterlogging, same quads and bytes) against 39.8-41.0 ms without them (the same as before slabs existed, compared in one process; 106,971 quads), and 99.2 ms with water, double slabs, waterlogged slabs and stairs and corner stairs there (`mesh-128-mixed-shape-chunks`). | Their faces, cube faces and liquid faces beside them are meshed per quarter face with half-block AO and light; a chunk with solid ones gets one more physics triangle mesh. | Half-block shapes only: no slopes, no slabs of two materials in one cell (a double slab is one block id), and a waterlogged cell holds only its type's `waterlog` liquid as a full source (no flowing level). VOX files have no shapes, so `.vox` imports are whole blocks. | Whole blocks where shapes are not needed; leave `TraceModel.shapes` out to trace whole cells. |

## Rendering

| Limit | Starts at | Why | What you see | Escape hatch |
| --- | --- | --- | --- | --- |
| One directional light in core | Enforced by design: core's lighting is one direction and one radiance, plus a colourless scalar ambient. | Every light model beyond one sun is an optional package, so apps that need one sun pay for one sun. | No API for a second sun in core; core's own ambient does not light metals. | `@margoengine/clustered`: up to 1,024 point and spot lights (`RangeError: Expected at most 1,024 lights` past that). `@margoengine/clustered/shadows`: shadows for up to 16 of them ([local-shadows-gpu.json](../examples/package-benchmarks/results/local-shadows-gpu.json)). `@margoengine/clustered/area` (8,946 B gzip): up to 64 rectangle area lights (`RangeError: Expected at most 64 area lights`), unshadowed, no texture bindings ([area-lights-gpu.json](../examples/package-benchmarks/results/area-lights-gpu.json)). More directional lights: `@margoengine/clustered/directional` (1,563 B gzip), up to 16 (`RangeError: Expected an array of at most 16 directional lights`), unshadowed. IES profiles: `@margoengine/clustered/ies` (3,697 B gzip), at most 16 distinct profiles, type C files only. Projector spots: `@margoengine/clustered/projector` (2,618 B gzip), at most 16 images of up to 4,096 texels a side. Physical units: `@margoengine/clustered/units` (833 B gzip). All three light entries use storage buffers, no texture bindings ([light-features-gpu.json](../examples/package-benchmarks/results/light-features-gpu.json)). Configurable ambient: `@margoengine/environment` `HemisphereLight` and `AmbientLight`, one per engine. Image-based lighting: `@margoengine/environment`. |
| 16 sampled textures and 16 samplers per shader stage | Enforced by WebGPU's guaranteed minimum; Margo's device asks for no more. gltf-pro's physical material with directional shadows, IBL and local shadows uses exactly 16 (table in the [gltf-pro README](../packages/gltf-pro/README.md#texture-bindings); asserted in [instancing.test.js](../packages/gltf-pro/tests/instancing.test.js)). | Every adapter, phones included, supports 16. Requiring more would make the same app fail on some devices. | A `RangeError` naming the combination, e.g. `gltf-pro: physical material + shadows + environment:lighting + clustered + clustered:shadows + shader patch needs 17 sampled textures per shader stage; this device allows 16`. | Drop one lighting feature for that material, or use the standard material (8 of 16 with everything attached). `VolumetricFog`, SSAO, clustered lights, area lights and light probes (`@margoengine/environment/probes`: one storage buffer; with an environment fallback they take EnvironmentLighting's place and its bindings) add no textures. Texture arrays are planned after 1.0. |
| float32 coordinates | Measured on the GPU ([large-coordinates-gpu.json](../examples/package-benchmarks/results/large-coordinates-gpu.json), 10 mm part, camera 50 mm away): core alone jitters 0.38 px at 1 km and 42 px at 100 km; at 6,000 km the part is not drawn. Per-stage CPU breakdown in [large-coordinates.md](large-coordinates.md). | Core and its kernel store positions and matrices in float32: half the memory and bandwidth of float64, and the format GPUs consume. | No error. Parts shake while the camera moves, small features collapse, specular shifts (2.8° at 100 km), and far enough out geometry disappears. | `FloatingOrigin` in `@margoengine/cameras/origin` (1,258 B gzip, 0 core bytes): 0.019 px jitter at every distance up to 6,000 km, and `engine.pick` hits the part at every distance ([large-coordinates.md](large-coordinates.md#the-plugin)). Vertices or child offsets that are already kilometres from their root inside one asset must be re-centred at export. |
| Transparency | Default: transparent materials and gltf-pro `BLEND` primitives are sorted back to front per mesh; core meshes are opaque. Measured ([oit-gpu.json](../examples/package-benchmarks/results/oit-gpu.json), a 50 % housing over gears orbited 360 × 1°): 13 steps with more than 1 % of covered pixels popping. | Sorting is exact for separate objects and needs no extra targets. | Popping where transparent parts interpenetrate or nest, as the camera moves. | `@margoengine/oit` (2,210 B gzip): 0 popping steps on the same orbit. Weighted blended OIT is an approximation: colour error against exact blending 0.5 / 4.6 / 8.7 (0-255) for 1 / 2 / 4 layers. Transmission and custom blending keep the sorted path; limits in its [README](../packages/oit/README.md#limits-the-wboit-approximation). |
| Screen-space reflections | Enforced by method: only what is on screen reflects. Core meshes and models passed to `ssr.add(model)` (gltf-pro, materials, terrain, water) show reflections; other custom shaders are reflected but do not reflect. Cost measured on a worst-case glossy floor ([ssr-gpu.json](../examples/package-benchmarks/results/ssr-gpu.json), quiet-gated): 2.2-2.3 ms at 1280×720, 5.8-5.9 ms at 1920×1080. | Reusing depth and colour that are already rendered avoids a second scene pass. Each custom pipeline needs its own capture into SSR's targets. | Reflections fade at screen edges and miss off-screen objects (reflection probes fill in where attached); water and terrain not added keep their own sky reflection. | `@margoengine/post/ssr` (9,068 B gzip) is itself the opt-in. Off-screen reflections: reflection probes in `@margoengine/environment/probes`; SSR removes the probes' own specular only where its ray hits on screen and keeps the probe's reflection elsewhere ([probes-gpu.json](../examples/package-benchmarks/results/probes-gpu.json): off screen the floor equals the frame without SSR, 95th percentile 0/255). Limits in the [post README](../packages/post/README.md). |
| Volumetric fog | Enforced by design: one froxel grid (default 160 × 90 × 64) whatever the screen size, so shadow edges in the fog are about one froxel wide (8 × 8 px at 1280 × 720). Effects measured in [volumetric-gpu.json](../examples/package-benchmarks/results/volumetric-gpu.json). | A froxel volume makes light shafts follow real shadows at a fixed cost per frame. | Particles, VFX, splats and transparent surfaces drawn after it are not fogged; nothing beyond `range`; no local fog volumes or multiple scattering. Errors: `RangeError: Volumetric grid exceeds device limit`; `VolumetricFog replaces environment Fog '<name>': set its enabled = false or remove it`; `VolumetricFog needs scene depth: attach a post capture (Tonemap, Bloom, PostStack, SSAO, TAA) first or pass options.depth`. | `@margoengine/environment/volumetric` (6,923 B gzip) is itself the opt-in: a finer `grid` sharpens edges at a higher cost; `fog.texture` lets custom shaders (particles) sample the fog. Limits in the [environment README](../packages/environment/README.md). |
| Light probes (indirect light) | Enforced ([probes.ts](../packages/environment/src/probes.ts), [probes.test.js](../packages/environment/tests/probes.test.js)): one irradiance volume of at most 4,096 L1/L2 probes (64 per axis) and at most 16 box-projected reflection probes per `LightProbes`. The volume is baked; reflection probes are baked or captured live a few cube faces per frame (`setLive`; a moved box shows in a 128 px probe 7-11 frames later at one face per frame, capture GPU time per frame 0.066 ms or less and a median 0.20 ms on the prefilter frame, RTX A6000, [probes-live-gpu.json](../examples/package-benchmarks/results/probes-live-gpu.json)). Measured bake of 8 volume probes and one 128 px reflection probe 114-121 ms (diagnostic: other jobs running; [probes-gpu.json](../examples/package-benchmarks/results/probes-gpu.json)). Accuracy in the same file: volume SH within 1.7% of DC against an analytic room. | Baking turns the scene's light into lookups (no ray tracing per frame) and keeps them in one storage buffer, so no texture binding is spent. | Volume light stays as baked until `bake()` runs again; live reflection probes lag the scene by up to (probes + 1) refreshes of 6 / `facesPerFrame` frames and see only what the frame draws (render with `culling: false`); light leaks through walls thinner than the probe spacing (no visibility per probe); mirror-sharp reflections show texel-sized steps near wall edges at the default 128 px. Errors: `RangeError: Invalid irradiance volume: min < max, 1-64 probes per axis (4,096 in total), sh 1 or 2, blend >= 0`, `RangeError: Expected at most 16 reflection probes`, `RangeError: Light probe buffer exceeds device limit`, `light-probes replaces EnvironmentLighting: pass {environment} to LightProbes instead of attaching both`. | `@margoengine/environment/probes` (14,984 B gzip) is itself the opt-in: re-bake on demand or capture reflections live, one volume box per room against leaks, a finer `resolution` for sharper reflections. Dynamic GI: none yet. |
| Projected decals | Enforced ([decals.ts](../packages/post/src/decals.ts)): 4,096 decals per `setDecals`, all drawn every frame (no culling); colour only. Cost measured (diagnostic: other jobs running; [decals-gpu.json](../examples/package-benchmarks/results/decals-gpu.json)): 1280 × 720 4x, 1.64 ms without, 1.64 / 1.97 / 6.36 ms with 1 / 16 / 256 one-metre decals. | Screen-space decals need no change to any material shader: one pass reads the scene depth a post capture already provides. | `Decals need scene depth: attach a post capture (Tonemap, Bloom, PostStack, SSAO, TAA) first`; at 4x MSAA decal edges along silhouettes are per pixel; gltf-pro BLEND primitives are tinted with the surface behind them; `multiply` cannot lighten and nothing changes normals or roughness. | `@margoengine/post/decals` (4,118 B gzip) is itself the opt-in; `mode: 'over'` for light-on-dark marks. Normal and roughness decals: none yet. |

## Platform

| --- | --- | --- | --- | --- |
