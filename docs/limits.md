# Design envelope

Margo is a small WebGPU engine: core plus the stage facade is 22,859 B gzip (`npm run measure:size` prints the exact figure; the build fails at 25,000 bytes; core alone is 21,468 B of its 21,504 B cap; the 2026-10-30 core cleanup, which removed the view target depth copy pass, `mesh.euler` and four small duplicates, took core from 21,176 B to 20,790 B and core + stage from 22,580 B to 22,189 B; storing a caller's 4x view target depth then added 23 B to each, a package's frame in one render pass 293 B to core + stage, and `Engine.renderTarget` 44 B), and every
other capability is an optional package. That size is a decision, and so are the boundaries below. Each one exists
for one of two reasons: it keeps core small and frozen, or it follows the limits WebGPU guarantees on every adapter
(Margo's device requests none above them, so an app that runs on a laptop also runs on a phone). This page lists every
hard limit, where it starts, what you see when you reach it, and the package or tool that takes you past it.

How to read "Starts at":

- **Enforced**: an exact constant in the source (linked), usually with the test that asserts it.
- **Measured**: a committed result file (linked). Unless a row says otherwise: ASUS Zenbook S 14, Intel Core Ultra 7
  258V with an Intel Arc 140V integrated GPU, Windows 11, Edge 155, AC power, GPU lock held.
- **Not measured**: the boundary exists, but nobody has run the case. No number is given.

Every number here has a row in [whitepaper/claims.md](whitepaper/claims.md) (LIM-001 to LIM-300). Past losses and their
fixes are in [whitepaper/perf-history.md](whitepaper/perf-history.md).

| Entities (core meshes, assembly nodes included) | Enforced: 8,388,608 slots (2^23; [kernel.ts](../packages/core/src/kernel.ts), [core-dirty-transforms.test.js](../tests/core-dirty-transforms.test.js)). The store starts at `capacity` (default 1,024) and doubles on demand. Measured ([results-scale-node.json](../examples/package-benchmarks/parts/results-scale-node.json), Node 24, quiet-gated): 352.1 B of kernel memory per slot at 1,048,576 slots (351 B by layout); a static kernel tick costs 3.3 ms at 100,006 entities, 20.2 ms at 499,992 and 41.5 ms at 1,000,012. Above 1,048,576 slots: not measured. | One float32 structure-of-arrays Wasm kernel computes every transform, bound and visibility. It is the reason core is small and fast, and its per-entity cost is linear: about 41 ns per entity per frame even when nothing moves. | Growth is automatic. Past the cap `createMesh` throws `RangeError: Capacity`; `Engine.create` with a larger `capacity` throws `RangeError: Capacity: 1..8388608`. A growth that cannot allocate throws and leaves the store as it was. Before the cap, frame time grows with entity count. | `@margoengine/culling`. `CulledInstances` keeps parts out of the entity store entirely: 0.41-0.55 ms CPU per frame at 89,883 parts, flat in part count ([results-culling.json](../examples/package-benchmarks/parts/results-culling.json)); parts lose picking, hierarchy and section caps. `CulledMeshes` GPU-culls parts that must stay core meshes; it removes GPU work, not the kernel tick. |

| Shader variants per engine | Enforced: 64 cached pipeline variants ([renderer.ts](../packages/core/src/renderer.ts)). | Biome world streaming (`@margoengine/biomes/view`) | Enforced by the check `packages/biomes/tests/flythrough-check.mjs` (run by `check:merge`): a 300 km/h flight over the zero-config world, tiles made by 4 workers as the camera goes, may add at most 0.3 ms to the slowest 1 percent of frames and 1 ms to the worst frame against the same flight with every tile made first; the page spends at most `budget` (default 0.25 ms) a frame sending jobs and copying tiles in. Tile jobs reuse their working arrays: placing the next tile makes 2.1 MB of fresh arrays (24.0 MB before) and a view tile 0.2 MB (4.6 MB before), and a tile's view and placement jobs share one world tile instead of making it twice (`packages/biomes/tests/tile-memory.test.js`). Measured on the RTX A6000 desktop, Edge 156: p99 +0.20 ms, worst +0.00 ms; 111 tiles needed in a flight, 2 arrive after the camera needs them, tile latency p99 337 to 348 ms. On the coordinator's laptop (Ryzen 7 7735HS with a Radeon 680M, 4 workers), three runs from a cool start at the landed code: p99 +0.1, +0.0 and -0.3 ms, worst +0.3, +0.9 and +0.6 ms (before these fixes: p99 +0.3 to +0.6 ms, worst up to +1.8 ms); its prefetched flights themselves vary from run to run (p50 0.8 to 1.4 ms), so a negative figure is that variation, not a gain. | Workers that threw away megabytes of fresh memory per tile slowed the page's own frames on a laptop APU (Ryzen 7 7735HS with a Radeon 680M: cores share memory and power) and failed the check there (p99 +0.3 to +0.6 ms). The fixes on that laptop: a frame sends the jobs it plans within its budget and a frame that plans leaves sending and copying to the next; a send starts only when the budget left covers what a send that reached a worker took lately (a job that only waits in the pool's queue costs nothing and does not count), while copying goes on while budget is left; terrain tiles go in a band of rows at a time; objects have scatter slots for every tile a view keeps (the laptop once ran out of them: `ScatterTiles has no free slot`). The plan of a still camera comes 30 frames after the last plan, not every 30th frame (it once fell right after a plan of the moving camera, and that second plan streamed too: 1 run in 5 failed the plan-frames check); three cool runs with that fix: p99 +0.1, +0.1 and +0.2 ms, worst +0.8, +0.8 and +0.3 ms. The landed code (b8210cd3), three runs: 2 of 3 pass; run 1 p99 +0.1, worst +0.6 ms; run 2 p99 +0.1, worst +1.0 ms, exactly at the limit; run 3 fails: p99 +0.4 ms against 0.3, worst +0.4 ms; every plan, send and packing line was clean in all three. Counting all runs of this streaming code on that laptop, 8 of 9 pass. The one miss is 0.1 ms (one timer step) over the p99 limit, in a run whose streamed flights had fewer frames (703 to 1,083 against about 1,150 to 1,200). On a 680M integrated GPU the margin is thin and the check can miss by one timer step; on the RTX A6000 it passes with p99 +0.10 to +0.20 ms. The limits were not loosened. Figures are medians of three flights per kind. Every worker still runs at once: a fixed cap of half the workers was tried and dropped, it made tiles late on that laptop and cost fast machines late tiles too. | Each world keeps its tile working arrays and each placement its candidate tables between tiles (about 15 MB per worker at the default 256 m tiles) until disposed. The view entry is 7,514 B gzip, over its earlier 7,374 B quality budget; up to 7,516 B accepted by Scott 2026-10-29. | `workers` on `BiomeWorld.create`; `budget`, `lookahead` and `radius` on `BiomeView.attach`; `view.prefetch(rect)` before a planned flight. |
| Biome world CPU speed (`@margoengine/biomes`, goal G1) | Missed: the goal is 400 ms per km2 on one thread (fields plus placement of R16 at 1 m), and this machine measures fields 376 to 444 ms (best and middle of 30 tiles, RTX A6000 PC with other jobs running) plus placement 177 to 222 ms. On 8 workers each replica makes the 9 whole tiles a placed tile reads, so neighbours are made more than once (`bench/biomes/placement.mjs`). What holds it: exact integer fields per cell (CORDIC aspect, Catmull-Rom heights, climate). The GPU path (row 27.4 B8) is the designed route to the goal; the goal is unchanged. Quiet-machine numbers come with the biomes benchmarks. |
| Biome objects beyond `radius` (`@margoengine/biomes/view`) | Stored trees, shrubs, rocks and props are drawn only for tiles within `radius` (default 1,000 m) of the camera, and grass and other detail within `detailRadius` (default 120 m). Trees go on to `far.radius` (default 2,500 m) as 12-triangle stand-ins over the world's canopy cover; shrubs, rocks and props stop at `radius`. Measured at the default: the zero-config world holds 162,776 streamed objects in 12.0 MB of GPU memory, 5.9 MB of it records and rings and the rest scatter's cull in candidate order (Rendering, "Scatter cull in candidate order"; `packages/biomes/tests/objects-check.mjs`, RTX A6000, 2026-11-05). Held objects grow with the area inside `radius`, so about four times as many at 2,000 m (expected from the area, not measured). | A stand-in is one coloured solid, hashed over the cover, not the placed tree: impostors or a far LOD of placed records would be a new scatter system, kept out of v1.0.0. | Stand-ins are lit by the engine light and cast no shadow; past `far.radius` far hills keep the darker canopy ground only. | Raise `far.radius` and `far.count`, or `radius` (memory and placement work grow with its square); `far: false` and your own far layer. |
| Biome root entry and GPU backend (`@margoengine/biomes`, accepted difference in size, Scott 2026-11-05) | Measured with `npm run quality -- --gate=sizes` (2026-11-05): root 16,329 B gzip, 553 B over its old 15,776 B budget and 329 B over the spec's 16,000 B; the GPU kernels are the lazy `@margoengine/biomes/gpu` entry, 21,714 B (14,425 B before it also took the flow and placement kernels a backend `'gpu'` world routes `hydrologyOfAsync` and `BiomePlacement` through), which only a world that may compute on a device downloads. Before the kernels moved out the root was 24,637 B. | The root bytes buy backend `'gpu'` and its `device` option (a small hook; checks, bands, device loss and kernels sit in the GPU entry), per-caller tile cancellation (one caller's abort no longer rejects a cached tile other callers wait on), an `update()` that leaves the world unchanged when a change throws, one revision of the world per request across awaited GPU bands, and the crop and pack step the CPU and GPU paths share. About 214 B came earlier from the J5 classify split and field validation. | A CPU world downloads the root only; a GPU world adds the GPU entry once. | `backend: 'cpu'` (or `'auto'` without a device) never loads the GPU entry. |
| Biome worker file (`dist/workers/biomes.js`) | Measured with `npm run quality -- --gate=sizes`: 43,778 B gzip (2026-11-05; 41,312 B before the erosion entry and the GPU placement and hydrology routing, 39,182 B before the J5 and GPU work), against the design's first estimate of about 18 kB. The worker build swaps the GPU entry for an empty stub ([worker-empty-stub.js](../scripts/worker-empty-stub.js)), since a worker's world never gets a device. Lazy: only a world created with `workers` loads it, and it counts toward no entry's budget. | A worker runs the whole tile path by itself: world, region, relief, erosion, placement, cover, zones and the view's tile functions (erosion is in the worker so a relief world with `erosion` gives the same bytes on 1 and 4 workers, about 2 kB; root about 15 kB, placement 11.9 kB, relief 4.3 kB, zones 3.6 kB, cover 3.4 kB). Reaching 18 kB would mean taking one of those out of the worker, so it would do less of the tile. | A world with `workers` downloads this one file, once; every worker shares the browser's copy. | Leave `workers` off and tiles are made on the page's thread. About 2.6 kB (digest and presets) is unused on the worker path; taking it out needs a change to the shared package build. |
| Biome rivers (`@margoengine/biomes/view`) | Fixed for v1.0.0: river and lake water stands still (`water: { rivers: 'auto' }` or `'hydrology'`, 1.5 m over the bed, falling with it; `lakes: 'auto'` at the hydrology's fill level); it does not flow. Off by default. | A flowing river needs the shallow-water passes to run on steep beds at a cost not yet measured, so it comes after v1.0.0. The view couples at most 512 water cells a side (16 m on an 8 km world). | Valleys are dry unless asked for. A river under two cells wide can break up, and past 0.375 of the world's side from the camera the water grid coarsens. | Attach your own `Water` with `terrain`, `fill` and, for the flow, no `still`. |
| Frame allocation (JavaScript heap per steady-state frame) | Measured by the check `npm run test:frame-alloc:browser` ([frame-alloc-browser.mjs](../scripts/frame-alloc-browser.mjs), scenes in [tests/fixtures/frame-alloc](../tests/fixtures/frame-alloc/main.js); run by `check:merge`). RTX A6000 desktop, Edge 156 headless with `--enable-precise-memory-info`: `performance.memory.usedJSHeapSize` read once per frame, 600 warm-up frames (one of them, 60 before recording, late on purpose: a 200 ms stall, so the floors hold for the steady state after a late frame) then 600 recorded, frames with a garbage collection left out, the median frame, largest of three runs, at the item 53.1 commit (`perf(core, shadows, post)`, 2026-10-29). Per frame, before and after (two steps, item 53.1 parts 1 and 2): three lit meshes 1,428 B to 340 B; 10,000 moving instanced boxes 1,076 B to 292 B; the same room with cascaded shadows and eight moving casters 26,920 B to 860 B; with SSAO, Bloom, tone mapping and FXAA 5,116 B to 1,528 B. The room plus 10,000 `DynamicInstances` boxes (@margoengine/culling), every row rewritten each frame through bulk writes and `update()`, measured 396 B in three runs at the item 53.2 commit (56 B over the room alone, among them the 16 B wrapper of its compute pass). The check fails when a median frame passes these floors; they are only ever lowered. | Every byte a frame allocates is a byte the garbage collector must sweep later, and a collection in the middle of a frame is a stutter. Margo reuses its arrays, descriptors and callbacks from frame to frame instead of making new ones. | Not 0 B, and it cannot reach 0 B: every WebGPU call that returns an object (the command encoder and its finished command buffer, each render pass, the canvas's current texture and its view) hands back a new 16 B JavaScript wrapper from the browser, and V8 stores the fractional frame time it passes to frame callbacks and plugins as a heap number. Shadows and post-processing add passes, so they add wrappers. Measured and left as they are: the frame-resources view set clears about 120 B per frame in the post scene (a fix changes the protocol between copies of the resources, judged risky for a frozen core), the SSAO scene walk makes an iterator and an options literal, the fixture setters box about 216 B in the shadowed scene, and each returned WebGPU object costs 16 B. Number boxing in V8's middle tier (Maglev) is gated too: `tests/frame-alloc.test.js` fails a core frame over 780 B, shadows over 620 B and the cascade fit over 128 B there on V8 14 (Node 26) and newer. V8 13 (Node 24, the minimum Node) passes the core limit (628 B) but its Maglev calls Math.sqrt with a boxed argument and result, 32 B a call, so it has its own row for the other two: shadows over 1,120 B (measured 1,081 B, 704 B of it 22 square roots) and the cascade fit over 256 B (measured 242 B, 224 B of it 7 square roots); a square root in JavaScript arithmetic with the same bits would cost every engine more time. Node 22 has no Maglev by default, so the middle-tier probes skip there. A late frame once deoptimized core's frame loop (its delta clamp first ran a compare on a frame past `maxDelta`, with no type feedback), and the loop then ran its next thousands of frames in a tier that boxes numbers: 24 to 84 B more per frame in every scene, seen only when `check:merge` loaded the machine. Fixed in core, and gated twice: the browser check's late warm-up frame, and `tests/frame-alloc.test.js`, which fails when a late frame leaves the loop unoptimized. The Node probes compile on the main thread (`--no-concurrent-recompilation`), so a package build running beside them cannot make them measure a lower tier. `npm run test:frame-alloc:nodes` runs the test on every Node it finds; the probes leave out windows in which V8 collected garbage. In these runs 0 to 3 of 600 recorded frames held a collection. | Keep your own `onFrame` callbacks allocation-free (the check's scenes keep their clock in a `Float64Array`). `node scripts/frame-alloc-browser.mjs --profile --source` names the functions that allocate per frame. |
| Moving transforms per frame (CPU budget) | Measured by [transforms-budget.mjs](../examples/package-benchmarks/transforms-budget.mjs): every mesh sets `position.y` and `rotation.y` through the setters each frame, one shared geometry and material (one instanced draw), all in view, Node v26.12.0 on an AMD Ryzen 9 9950X (32 threads), a stand-in GPU device so the figure is the CPU work only (the onFrame callback, the Wasm kernel tick, instance patching, the renderer's frame). 120 warm-up frames, 300 timed, the median frame, a binary search for the largest count within 4 ms (a quarter of a 60 Hz frame). Run the script on your machine. |

Flying at 11 blocks/s while chunks stream in: frame CPU p95 3.7 ms (render distance 8) and 5.0 ms (16), worst frames 6.8 and 10.2 ms; back to back with the code before 2026-10-20 at 16: 4.2 / 8.1 ms before, 3.9 / 7.4 ms after. Laptops and phones: not measured. | Each loaded chunk keeps its block palette and light on the CPU; each chunk with faces keeps 12-byte quads in one GPU pool (`maxQuadBytes`, default 96 MiB); generation and meshing run in workers, joining and light on the main thread spread over frames (`chunksPerFrame`, `frameBudget`); chunks above a column's ceiling, when the generator gives one, load as air without a job. | Filling the range takes time in proportion to the chunks in it, about 1,550 chunks a second here with a 2 ms join budget (about 680 with the default 0.5 ms, which keeps frames light during play). Worlds wider than float32 precision (about 100 km) jitter: voxels have no floating origin in v1 (packages/voxel/DESIGN.md, decision 4). | A smaller `distance` on `VoxelStreamer`; a larger `frameBudget` and `chunksPerFrame` while a loading screen shows; a larger `maxQuadBytes` (up to the device's storage binding limit); more `workers` for the mesher and streamer. |

| 16 sampled textures and 16 samplers per shader stage | Enforced by WebGPU's guaranteed minimum; Margo's device asks for no more. gltf-pro's physical material with directional shadows, IBL and local shadows uses exactly 16 (asserted in [instancing.test.js](../packages/gltf-pro/tests/instancing.test.js)). | Every adapter, phones included, supports 16.
