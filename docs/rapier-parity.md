# Rapier parity and beyond: physics tracking file

Scott's order, 2026-11-07: Margo's own physics must have every feature and every option Rapier has, one for one, in newer and cleaner code, and do more where it can. A second order the same day: "the most powerful feature rich physics engine possible". This file tracks both. Part 1 is the floor, Rapier parity, and it comes first. Part 2 is everything past Rapier.

**Reference.** Rapier 0.36.1 (the `rapier3d` and `rapier2d` crates on docs.rs, Rust user guide 0.36) and `@dimforge/rapier3d` / `@dimforge/rapier2d` 0.21.0 (JS user guide 0.21), inventoried on 2026-11-07. Rapier is Apache-2.0 and is the reference only by name. The inventory was taken clean room: from the public user guide at rapier.rs/docs (Rust and JS, 2D and 3D), the JS API reference pages and the docs.rs type and method pages. No source repository file, no source view page and no example or benchmark code was opened, and nothing beyond names was copied. Part 2 was taken the same way, from public documentation and feature lists only. Rapier's names appear here so a row can be checked against its docs; Margo keeps its own names (the root entry's, in `packages/physics/README.md`) and the row says which one maps to which.

**Where Margo stands.** Since 2026-11-24 the root entry `@margoengine/physics` runs on Margo's own solver, a Rust kernel compiled to WebAssembly (`packages/physics/kernel`), and ships no Rapier; Rapier 3D is a root devDependency that comparison tests load as a black-box oracle and is never shipped. `@margoengine/physics2d` runs on Margo's own 2D kernel too (since 6f436d2e9); `rapier2d` is only an optional comparison module outside the repository. Parity is judged on the own solver: a row is done when the own solver has it with a test. The 3D collision and query rows are in [physics-collision-parity.md](physics-collision-parity.md), each with its test.

**Backends.** The engine renders on WebGPU and falls back to WebGL2 (`@margoengine/webgl2-compat`, a WebGPU-shaped device on WebGL2, and the smaller `@margoengine/webgl2-compat/preview` preview). Every physics feature must work on both. The kernel is CPU WebAssembly, so it runs the same bits whichever backend draws the frame: a row marked `Wasm` in both columns needs no GPU at all. A feature with a GPU path also needs a WebGL2 path (the Wasm kernel, or WebGL2 render-to-texture or transform feedback) that gives the same results within the same tolerances, and its tests run on both. Where WebGL2 cannot reach the same speed, the row says so as an accepted difference with its cause.

**What assumes WebGPU today (checked 2026-11-07, origin/main e0e6494da).** Nothing in `packages/physics/src`, `packages/physics/kernel`, `packages/physics2d/src` or `packages/ragdoll/src` touches `navigator.gpu`, a GPU device or WGSL; the Node tests of all three already run against a mesh renderer stub that says `backend: 'webgl2'`. Two gaps: (1) the physics browser test (`packages/physics/tests/physics-browser.js`) reads pixels back through WebGPU only, so no browser test runs physics on the WebGL2 backends; (2) `debugRender()` buffers are drawn with `@margoengine/lines`, which draws on `webgl2-compat`; on the `@margoengine/webgl2-compat/preview` preview backend `Lines` refuses at setup with a linked `unsupported` error and draws nothing (its README, Limits). Both are rows below (W-01, W-02).

| Status | Meaning |
| --- | --- |

# Part 2: Beyond Rapier

Every feature here is an optional, tree-shakable entry or package, never core and never a cost for an app that does not import it. Size and speed claims are measured. Engines named: Jolt, PhysX 5, Bullet (with pybullet), MuJoCo, Havok, Box2D v3 and Unreal Chaos, from their public docs and feature lists only; a name marked (u) was not confirmed from a fetched page and must be checked before any public claim. Papers are to be fetched and read in full by the job that builds the row; a DOI marked (u) must be checked first. "Status" follows the key at the top: DONE only with a named test. Row ids never change once given, so a few numbers are unused. The fit columns say how each backend runs it; "GPU" rows run in WebGPU compute and, on WebGL2, in the Wasm kernel or a render-to-texture pass, with the same results within the same tolerances.
