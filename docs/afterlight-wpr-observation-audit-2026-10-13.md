# WPR command observation audit and private follow-up

The initial audit changed or executed no worker, recovery helper or caller; the implementation follow-up below is separately authorized and tested. The earlier timed-out recovery journal remains a failure; the later inactive inspection does not manufacture its unknown stop exit code. No actual WPR command, elevation, real ETL, browser, GPU or build was opened/run for either phase.

The current worker's `Invoke-OwnedWpr` uses a60s `WaitForExit` for start/stop, throws on timeout, then disposes its original Process object in `finally`. Its asynchronous ReadToEnd tasks expose text only after EOF, so live progress is not journaled. The recovery helper already pumps2048-character stdout/stderr chunks and heartbeat every250ms, but throws when its180s stop observation expires. That unwinds the function and ends the parent while the actual stop/merge can continue. Its post-loop Dispose is skipped on this error. A PID/start-time record is useful identity evidence, but does not retain the original Process.Start observation or guarantee recovery of its eventual exit code.

Smallest proposed change, confined to the two command functions and their selfchecks:

1. Keep the existing process object created by Process.Start, both redirected readers and pending reads alive until a `-start` or `-stop` process actually exits. Keep its status `running`, exitCode null and update heartbeat/elapsed/progress. At60/180s set an additive `observationDeadlineExceeded` flag and timestamp once; do not throw, retry, cancel, kill or dispose merely because that observation threshold passed. This is an observation deadline, not a terminal timeout or permission to launch another WPR command.
2. Use the recovery helper's existing chunk pump in the worker rather than ReadToEnd-only publication. Preserve carriage-return progress, stdout/stderr separately, and stream faults. Read `.Result` only after a pending task completes. Record actual exitCode/exitUtc immediately from the original process object, then allow the existing bounded5s terminal pipe drain. A child can be terminal while inherited pipe writers still keep EOF pending; preserve explicit pending flags and reject clean-success claims in that case. Dispose only after terminal process observation/drain handling. A stream fault must not abandon observation of a still-running mutating command.
3. Status/profiles commands may retain their bounded10s failure policy, with exact PID/start time and unknown exit retained when they time out. Validate each inspection result before launching the next status command; current recovery performs all three before checking them. No automatic retry is appropriate for a duplicate control library or ambiguous status.
4. Preserve ownership rules. No `ownedSession`, `started.json` or caller start success before actual start exit0 and complete, nonfaulted output observation. A late actual start success may establish ownership in the still-running worker and use its existing stop-request/max-window policy exactly once. A nonzero/ambiguous start never gives stop authority. Stop/merge remains `stopped:false` while the original child is running; a threshold flag is not a worker error or a final result. Successful stop claims should require actual stop exit0, completed streams, saved nonempty ETL and a successful fresh elevated inactive status. These are independent of the size/stability of a file still being saved.
5. Keep terminal command failures explicit: store command/exit code plus bounded stderr/stdout detail in the surfaced error and preserve full streams in artifacts. The saved [during-save inspection](../test-results/wpr-inspect-during-save-20261013T231442372Z/recovery-status.json) actually exited with signed code-984087039 (`0xc5580601`) and “Duplicate instance of Windows Performance Recorder Control library is running.” That is neither proof of a still-active capture nor proof of inactivity. Three duplicate-library failures must not become an accepted status.

Caller scope: retain the tracer's80s start and70s stop observation bounds; do not silently expand them to25minutes. If either bound expires, report pending/unverified with worker/job/child identity and latest heartbeat, while the independent elevated worker continues to own its original child and streams. Never accept a late start retrospectively as coverage for an already-failed measurement, and never issue a second stop because the observer timed out. `requestWprStop` already sets `stopRequested` before waiting, so its finalizer does not resubmit; preserve that behavior. The worker must publish nonterminal deadline flags outside `errors[]`, because both caller handshakes currently abort immediately on worker errors.

The normal tracing caller currently awaits WPR stop completion before `endTrace()`. A slow merge can therefore prolong CDP collection after the timed app window even though the app is stopped. A follow-up caller change should initiate the single stop request, drain/end CDP independently, then observe the worker result within the existing caller bound. This is diagnostic lifecycle handling, not a measured FPS improvement. Native WPR start/stop command latency also means `MaxSeconds` after start acknowledgement is not proof of an exact total kernel-recording interval; record command-request, actual-command-exit and acknowledgement times without relabeling them as proven kernel start/stop timestamps.

Test scope before any real elevation:

- Update `wpr-command-journal-selfcheck.ps1`: run the exact command function with only the executable substituted by ordinary Node children and a small injected observation threshold. A child that runs past the threshold then exits0 must retain the same PID, post-deadline heartbeat, incremental stdout/stderr and actual terminal exit; no ownership while pending. Include nonzero/duplicate-library detail and a still-bounded status command.
- Update `wpr-recovery-stream-selfcheck.ps1`: replace its existing expectation that a1s stop deadline throws. A1.5s ordinary child should cross the threshold, keep progress/heartbeat and then record actual exit0, complete streams and one invocation. Add stream-fault or inherited-pipe pending coverage without an unbounded `.Result`.
- Update `wpr-handshake-selfcheck.mjs`: matching-token running/deadline state remains unstarted and reaches the80s caller bound; late start is not retroactive. Matching running stop reaches70s as unverified with exactly one stop request; worker terminal success later remains separate. Actual nonzero errors fail immediately; wrong tokens and pending streams cannot authorize ownership.
- Preserve old harness copies, selfcheck outputs and failure journals. All new tests use ordinary naturally exiting children or mocked time, no WPR/UAC/native/GPU activity. Add no shared framework or package dependency.

## Implemented private follow-up

Both existing command functions now retain their original Process.Start handle, chunked stdout/stderr pump and heartbeat until an actual mutating command exit. The60s worker and180s recovery observation thresholds set a nonterminal flag/timestamp while status remains running and exitCode remains unknown; they neither throw nor retry/terminate a start/stop. Actual terminal exit code/time comes from the original process object. Post-exit pipe draining remains bounded5s, with pending/faulted streams making success unverified. Nonmutating status commands retain bounded failures. Recovery rejects each failed status before starting another inspection, and duplicate control-library detail/code is surfaced explicitly. No new framework or dependency was introduced.

The browser caller still observes start for80s and stop for70s. Its timeout now records observer expiration, pending command identity and that the worker may continue independently; it requests no worker termination. Reentering the stop observer sends no second stop request. The worker's existing eventual-success ownership and hard-MaxSeconds autostop remain intact. This patch does not add a new final inactive query to the owned worker or change the CDP-drain/merge ordering; fresh inactive inspection remains required by quiet mode. The broader caller-drain ordering recommendation above is deferred.

Ordinary Node children exercised both actual command pumps: delayed start and stop crossed150ms/1s thresholds, preserved one PID/creation identity and incremental carriage-return output, then supplied actual exit0 and drained streams. A nonzero7 child preserved duplicate-library text and0xc5580601; bounded ordinary status timeout children exited naturally without termination. The complete existing worker orchestration, with elevation/executable mocked only, acquired ownership after a delayed successful start and autostopped once at hardMaxSeconds1 despite an ended mock browser observer. All child PIDs were absent afterward. Nine mocked caller handshake cases passed, including repeat-finalizer no-second-stop checks, and seven quiet/native trace regressions passed.

Artifacts, tested source copies/hashes and prior selfcheck sources are saved in [the lifecycle selfcheck folder](../test-results/wpr-lifecycle-selfcheck-20261013T233307013Z). These tests prove private process-observation behavior with ordinary children, not successful real WPR capture or an FPS improvement. Old executed harnesses, recovery failures, unknown exit-code evidence and saved measurements are unchanged.

Root review identified a separate ownership edge: an actual start exit0 can create a recorder even if its inherited stdout/stderr pipes fail to drain. The private worker now establishes `ownedSession`/`startCommandSucceeded` immediately after proven native exit0, before checking stream integrity. A stream-integrity failure still records an error, publishes no valid started handshake and enters the owned single-stop finalizer. Nonzero or unknown start exits never create stop authority. A stop exit0 with incomplete streams remains unverified and is not retried.

Five focused mocked whole-worker cases passed: start0 with pending stdout, start0 with a stream fault, unknown start, nonzero start, and stop0 with pending stderr. The first two stop exactly once despite the failed capture; unknown/nonzero starts never stop; the last remains unresolved after one stop. Nine caller handshake regressions also passed. [New evidence and tested source hashes](../test-results/wpr-start-integrity-selfcheck-20261013T234054966Z) are separate from the preserved earlier lifecycle artifacts. These focused checks launched no child, WPR, UAC, browser or GPU process; prior ordinary-child suites were not repeated.
